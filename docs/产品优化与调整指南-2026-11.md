## 1. 宏观：这个产品站在哪

### 1.1 品类结构

Android 上的压缩/文件工具是一个**头部极稳、长尾极碎**的市场：

| 产品 | 量级 | 商业模式 | 强项 | 软肋 |
|---|---|---|---|---|
| ZArchiver | 长期居该品类安装量第一 | 广告 + 捐赠 | 格式全、包内浏览/选择解压、修复、2010 年代就形成的肌肉记忆 | 界面陈旧、广告、中文编码体验一般 |
| RAR (RARLAB) | 千万级 | 免费 + 广告 | RAR 官方实现、修复能力 | 只做 RAR 生态、UI 老旧 |
| 7Zipper | 百万级 | 广告 | 双栏文件管理、格式多 | 广告重、稳定性口碑一般 |
| Solid Explorer / MiXplorer | 百万级 | 买断/捐赠 | 文件管理专业度、云与网络 | 不是压缩工具心智，价格门槛 |
| Files by Google | 系统级预装，量级最大 | 免费 | 系统级、清理与分享 | 仅能解压 ZIP，无压缩能力 |
| **Zippest** | 早期 | 免费、无广告、平时不联网 | 无广告/平时不联网（1.12.0 起仅检查更新时联网）、GBK、分卷、批量密码、后缀重命名；**1.7.0 起补齐包内多选解压与单文件打开** | 认知为零、缺信任凭据 |

结论：**这个品类不缺"能用"的工具，缺"让我放心把重要文件交给它"的工具**。你的差异化不在格式数量（12 种压缩 / 17 种解压已经足够），而在信任与中文场景。

#### 1.1.1 能力对照（决定"补什么"的原始依据）

| 能力 | Zippest | ZArchiver | RAR | 结论 |
|---|---|---|---|---|
| 包内目录浏览 | 有 | 有 | 有 | — |
| 包内多选解压 | **无** | 有 | 有 | P0 |
| 包内单文件直接打开 | **无** | 有 | 有 | P1 |
| 压缩格式数量 | 12 | 多 | 仅 RAR/ZIP | 已够 |
| RAR 压缩 | 无（法律） | 无 | 有 | 不做 |
| 分卷创建 / 自动合并 | 有 | 部分 | 有 | 已领先 |
| GBK 编码切换 | 有 | 部分 | 部分 | 已领先，需曝光 |
| 批量密码复用 | 有 | 无 | 无 | 差异化 |
| 修复损坏包 | **无** | 有 | 有 | P2 |
| 校验和（SHA/MD5/SFV） | **无** | 部分 | 无 | P2 |
| 广告 | 无 | 有 | 有 | 差异化 |
| 网络权限 | **仅检查更新**（1.12.0 起，见 §0.3） | 有 | 有 | 差异化改为「平时不联网」 |
| 压缩断点续传 | 待验证 | 无 | 无 | 领先机会 |

结论很直白：**"补两个包内操作 + 暴露两个无广告/无网络卖点"就能在能力表上不输 ZArchiver**，剩下的修复、校验是加分项。

#### 1.1.2 用户分群（决定优先级，占比为经验估计）

| 人群 | 估计占比 | 典型场景 | 最在意 | 对应动作 |
|---|---|---|---|---|
| 普通用户 | ~60% | 微信/QQ 收到的压缩包、下载的 ROM/资料 | 能不能一键解开、别乱码、别弹广告 | 首启引导、完成态动作、GBK、包内打开单文件 |
| 资源囤积者 | ~25% | 网盘分卷下载、几十 GB 的素材包 | 分卷能不能合并、失败能不能续、删错能不能找回 | 分卷预检、断点续传、任务历史、回收站一级入口 |
| 极客/开发者 | ~15% | 刷机包、代码备份、批量归档 | 格式覆盖、校验、修复、批量与脚本化 | 校验和、修复、排除规则、批量重命名 |

这张表直接决定 1.7 的取舍：**完成态动作和包内操作服务 60% 的人，分卷预检服务 25% 的人，修复/校验只服务 15% 的人**——按这个顺序排，不会错。

### 1.2 你真正的差异点（按证据强度排序）

1. **平时不联网**：1.12.0 起为「检查更新」申请了 `INTERNET`，但只有用户点按版本号时才访问 GitHub Releases API，其余功能全部离线（见 §0.3）。这仍是可被第三方验证的硬承诺，全品类稀缺。**当前只有关于页与首启脚注提到它，没有把它当卖点**——这是最容易拿的一分。
2. **中文编码处理**（设置项"文件名编码"，[SettingsScreen.kt:423](C:/Decompress/android/app/src/main/java/com/decompress/app/ui/SettingsScreen.kt#L423)）。Windows 打的 GBK zip 在国行手机上乱码是高频痛点，竞品普遍做得敷衍。
3. **批量密码填充 + 后缀重命名**（`ArchiveScreen` 的 `samePassword` 流程、`selectedFileSuffix`）。是真需求，但属于"用了才知道"的功能，需要引导。

反过来说，**分卷、多格式、后台任务这些不是差异点，是入场券**——没有会被骂，有了不加分。

### 1.3 定位问题：两个形态互相稀释

现在它同时是"文件管理器"和"压缩工具"：

- 首屏是文件列表（`FileBrowserScreen`，约 1330 行），信息密度按文件管理器设计；
- 但真正的价值时刻发生在"打开压缩包 → 解压 → 完成"，而这条链路被塞在二级页面；
- 结果是：比文件管理器（Solid/MiX）浅，比压缩工具（ZArchiver）少了包内操作——**后半句 1.7.0 已补上（多选解压、单文件打开），前半句仍是差距。**

**建议定位**：「**给中文互联网的压缩包用的工具**——下载、微信/QQ 收到的包，解压、压缩、分卷、修乱码，全在本地，不联网。」

对应的三个落地动作：

| 动作 | 说明 | 工时 |
|---|---|---|
| 首屏加"压缩包"筛选 chip | 全部 / 压缩包 / 最近修改，一键筛出 `.zip/.7z/.rar/.001...` | 1 |
| 快速访问加"微信/QQ/浏览器下载" | 读 `tencent/MicroMsg/Download`、`tencent/QQfile_recv`、`Download` 目录，存在才显示 | 1.5 |
| 关于页加"隐私自证" | 展示"平时不联网，只在检查更新时联网"，附"如何自行验证"（设置 → 应用 → 权限 → 网络） | 0.5 |

### 1.4 商业模式：三条路，选一条就说清楚

| 方案 | 做法 | 优点 | 风险 |
|---|---|---|---|
| A 纯免费 + 捐赠 | GitHub Sponsors / 爱发电 | 与"无广告"人设一致 | 收入≈0，不可持续 |
| B 一次性买断 Pro | Play 内购解锁"压缩包修复、密码库、批量重命名"等进阶功能 | 变现清晰、可验证需求 | 需 `INTERNET` 或 Play Billing 权限，会破坏"平时不联网"卖点 |
| C 免费 + 周边 | 无付费，靠 GitHub 声誉反哺其他项目 | 零维护成本 | 无收入 |

**建议 A 或 C，短期不要碰 B**：一旦引入 Play Billing，就必须常驻联网，"平时不联网"这个最强信任状就没了。如果未来要变现，优先做"外部捐赠 + 企业定制"，而不是把功能关进付费墙。

| 国内应用商店 | 未上 | 软著、备案、隐私合规检测 | P2，投入产出比最低 |

### 1.6 度量：几乎没有联网行为，怎么做数据

现实约束：除用户主动检查更新外应用不发起网络请求，任何第三方 SDK 都不可用（这是好事）。行业里同类"离线优先"产品的做法是**本地数据 + 用户主动导出**：

1. **本地事件环形缓冲**（只存本地，最多 500 条）：任务开始/成功/失败、失败原因码、格式、体积分档、耗时、是否后台被杀。
2. **"导出诊断包"**（设置 → 关于 → 诊断）：生成 zip（`device.txt`、`build.txt`、`events.jsonl`、最近 logcat 环形缓冲），由用户通过系统分享发给开发者。**必须用户主动触发**，否则就违背隐私承诺。
3. **代理指标**：GitHub star / issue 速率 / Release 下载计数（GitHub API 可查）/ 酷安评分。
4. **崩溃**：`Thread.setDefaultUncaughtExceptionHandler` 落盘，下次启动提示"上次异常退出，是否导出报告"。不要自动上传。

这套方案的行业先例：F-Droid 生态、Termux、部分密码管理器（KeePassDX）都是"本地记录 + 手动导出"。

### D. 引擎与格式

**D-1 格式矩阵（P1，按需）**
现状：解压 17 种、压缩 12 种；RAR 只解不压（法律原因，正确决策）。
缺口（按用户价值排序）：`ISO`（镜像）、`CAB`、`XAR`、`ZIM`、`APK/JAR 内浏览`（已有 JAR 关联）、`LHA`（日系老包）。
建议：优先补 **ISO**（libarchive 原生支持）与 **APK 内浏览**（市场需求大、实现成本低：APK 就是 zip）。

**D-2 编码：从"全局设置"到"自动 + 局部覆盖"（P1，2 人日）**
现状：全局设置（设置 → 文件名编码）。
行业做法：UTF-8 失败 → 尝试 GB18030/Shift-JIS 启发式（非法字节率判断）→ 结果页给"乱码？试试 GBK"一键切换；全局设置只作为兜底。

**D-3 无修复能力（P2，3 人日）**
竞品有"修复压缩包"。可做：ZIP 用 `zip -FF` 等价逻辑（扫描本地文件头重建中央目录），RAR 走 `unrar` 的 `r` 逻辑不易做 → 先做 ZIP。
这是**口碑型功能**：论坛里"这个包坏了还有救吗"的帖子大量存在。

**D-4 校验和（P2，1.5 人日）**
生成 SHA-256/MD5，校验输入值；支持 `.sfv`。极客人群高频，成本低。

**D-5 安全（P1，已部分具备）**
已有：路径穿越、条目数限制、空间检查（`ArchiveSafetyTest`）。
补：符号链接（tar 里的 `../` 与绝对路径软链）、条目名长度（>255 字节）、同名大小写冲突（FAT32）、解压炸弹的压缩比阈值（>1000:1 警告）。

**D-6 性能（P1）**
- 大目录：`LazyColumn` 无分页，1 万文件时首帧可能卡；做法：分块加载（每 200 条）+ `key = uri`。
- 缩略图：每行 `LaunchedEffect` 现场解码，无内存缓存（[DecompressApp.kt:2150](C:/Decompress/android/app/src/main/java/com/decompress/app/ui/DecompressApp.kt#L2150)）；做法：接 Coil 3（`AsyncImage` + 内存/磁盘缓存 + 下采样），或自建 `LruCache<String, Bitmap>` 上限 1/8 堆。
- 进度上报：高频 `setProgressAsync` 可能拖慢；做法：节流 ≥200 ms。

**D-7 压缩断点续传（✅ 1.7.1 已实现，受限范围）**
做法：TAR / TAR.GZ / TAR.BZ2 / TAR.XZ 用「目标目录隐藏临时文件 + 64 MB 分段 + gzip/bzip2/xz 多成员拼接」实现；分段边界写 `CompressionResumeState`（条目数、上一条目名、文件偏移、源指纹）到 SharedPreferences，进程被杀后从偏移截断、新开压缩成员继续，完成后改名。
为什么 ZIP/7Z 不做：中央目录/文件头在末尾，续写要自写完整 ZIP writer（8–12 人日），竞品也都不做。
额外代价：写侧不重新压缩（CPU 0 增量）、不复制（空间 0 增量）；每 64 MB 多一个压缩成员，压缩率损失通常 <0.5%；临时文件在目标目录可见（`.zippest-partial-*`），7 天自动清理。
限制：只在直连存储目录生效（SAF 目标退化为一次性写入）；源指纹是「条目数 + 总大小 + 时间戳和 + 首尾名」，深目录内部改动识别不到；进程死于改名与清理之间的极小窗口时可能留下重复产物。

**E-1b AGP 的 ABI 拆分与 AAB 互斥（新发现，0.5 人日，已绕开）**

**E-3 APK 体积（✅ 已完成，1 人日）**
原状（`release/Zippest-1.6.1.apk`，13,053,653 B）：内含 7 个 ABI——`arm64-v8a 2.51 MB`、`armeabi-v7a 2.10 MB`、`x86 2.72 MB`、`x86_64 2.86 MB`，外加 mips 130 KB / mips64 150 KB / armeabi 127 KB 的纯垃圾（JNA 预编译包自带）。
落地做法：

```kotlin
android {
    defaultConfig { ndk { abiFilters += listOf("arm64-v8a", "armeabi-v7a") } }
    splits {
        abi {
            isEnable = !providers.gradleProperty("zippestBundle").isPresent
            reset(); include("arm64-v8a", "armeabi-v7a"); isUniversalApk = true
        }
    }
}
```

实测（1.7.0，versionCode 73）：

| 产物 | 体积 | 对比 |
|---|---|---|
| arm64-v8a 单包 | **4.87 MB** | −63% |
| armeabi-v7a 单包 | **4.47 MB** | −66% |
| universal（arm64 + v7a） | **7.01 MB** | −46% |
| AAB | **7.71 MB** | 原 10.17 MB |

解包复核：arm64 包内只有 `lib/arm64-v8a`；universal 只有 `arm64-v8a + armeabi-v7a`，mips/x86/armeabi 全部消失。
Play 走 AAB 后由 Play 按设备下发，用户实际下载约 4.5–5 MB。GitHub 以 arm64 单包为主、universal 兜底。

| 同名文件 | 选项含义不明 | 改成"遇到同名文件：跳过 / 覆盖 / 自动重命名" |
| 快速访问 | 与"内部存储"重复感 | 保持"快速访问"，根项写"内部存储" |

落地：

- 新增 `docs/terminology.md`：核心术语表 + 写法约定，作为文案与将来 i18n 译名的来源；
- `压缩文件` → `压缩包`（压缩面板标题 1 处 + 压缩引擎错误提示 3 处）；全仓库「提取」为 0 处，原本就以「解压」为主；
- `同名文件` → `遇到同名文件`（解压面板、设置项），选项 `重命名` → `自动重命名`（与顶栏「批量重命名」区分）；
- 分卷：未选分卷时补一行说明（把大包切成 `.001 / .002…`，解压时打开第一个），选了分卷后仍显示实际的产物文件名预览；
- 「快速访问」保持不变：区块叫快速访问，里面单个条目叫「快捷位置」，两者是层级关系不是同义词。

### 4.3 无障碍（✅ 已完成，2026-11-09，1.21.5）

证据：源码里 `contentDescription` 共 55 处，其中 27 处为 `null`（多数是与文字并排的装饰图标，可接受）；但列表行、缩略图、纯图标按钮缺少语义。
做法：`Icon` 装饰性可留 `null`，但**可点击的图标必须有描述**；列表行加 `Modifier.semantics { contentDescription = "文件夹 $name，$count 项" }`；用 TalkBack 走查三条主流程；字号用 `sp`（当前多处 `dp` 字号需核对）。

进展：

- 审计结果：**所有纯图标按钮（IconButton）都已有描述**（返回/搜索/新建/更多/取消任务/预览压缩包…），30 处 `null` 都是装饰性图标（行内 chevron、空态插图、缩略图占位）——符合规范，不改。
- 字号：全仓库没有 `fontSize = *.dp`，字阶都走 `MaterialTheme.typography`（4.1 已补全 13 档）。
- 列表行语义（1.21.5）：
  - 文件行 `EntryRow`：`semantics(mergeDescendants = true)` + `contentDescription = "名称，类型 · 时间"`，多选态加 `stateDescription`（已选中/未选中）；
  - 包内行 `ArchiveRow`：`"名称，文件夹/大小"` + 选中态。
- TalkBack 真机复验（1.21.5）：安装 Android 无障碍套件后开启读屏，文件列表各行念出「名称 + 类型 · 时间」，行级标签无遗漏，用户确认可用；任务行/回收站行的合并语义属锦上添花，后续随相关页面改动补齐，不影响本项验收。

验收：`uiautomator dump` 确认行节点带有 `content-desc="Download，文件夹 · 2分钟前"` 这类描述（1.21.5 真机通过），TalkBack 实际朗读确认（2026-11-09，用户复验）。

### 4.4 大屏与折叠屏（P1，3 人日）
背景：Android 16（targetSdk 36+）对**大屏忽略应用的屏幕方向/尺寸限制**，你的 `targetSdk = 37` 已适用。
做法：`WindowSizeClass` 断点（≥600 dp 双栏：左树右列表；≥840 dp 三栏）；预览页在宽屏用左右分栏（目录树 + 详情）。你本机三显示器，这既是适配也是自用体验。

- 长按多选要有触觉反馈（`LocalHapticFeedback`）
- 删除/移动用 `animateItemPlacement`，别整列表闪一下
- 进度条用线性 + 百分比数字，别只给不确定动画

### 4.6 反馈闭环（P1，1 人日）
现状：关于页有 GitHub 入口，但没有"带着上下文反馈"的路径——用户报 bug 只能说"解压失败了"。
做法（网络只用于检查更新，反馈走本地生成 + 系统分享/浏览器）：

1. 关于页 → **反馈**：弹出一个预填好 `versionName + versionCode + 机型 + Android 版本` 的文本，用户可"复制"或"发送到邮箱/GitHub"；附带"生成诊断包"（见 1.6）。
2. 仓库加 `.github/ISSUE_TEMPLATE/bug_report.md` 与 `feature_request.md`，要求填版本、格式、体积分档、是否加密/分卷。
3. 每个 issue 用固定标签：`bug / format-support / ux / needs-device-test`；回复模板先给"临时绕过办法"。

这会显著降低"不知道为什么失败"的沟通成本——你现在的失败信息本来就不够，用户复述一遍又是一层损耗。

## 8. 视觉与交互：美术指导视角

> 这一章不做功能判断，只看"像不像一个成熟产品、用起来顺不顺手"。证据来自 `Theme.kt`、UI 源码扫描和 1.8.0 真机截图；每条都给到可执行参数与行业通行做法。

### 8.0 总判断：基调对了，体系没落地

视觉基调是"纸感工具"：`#F6F7F5` 暖灰底 + 纯白卡片 + `#0F6B4F` 深绿主色，克制、可信，适合离线工具。问题是没有统一体系在管它：

- 23 处直接写死的 `Color(0x…)` 绕过主题；
- 26 处圆角用了 7 种取值，间距用了十几种；
- 全 App 只有一处动画，还是装饰性的无限呼吸光；
- 空态、加载、错误三态各写各的。

结果就是"看起来像三个人做的"。下面按 色彩 → 字排 → 栅格 → 图标 → 动效 → 三态 → 交互 → 无障碍 → 深色/大屏 逐项给方案。

### 8.1 色彩：主题只定义了一半

现状（`Theme.kt`）：浅色/深色各定义了 12 个角色（primary、primaryContainer、background、surface、surfaceVariant、outline、error…），其余沿用 Material 3 默认值。UI 里还用了 `secondary`、`secondaryContainer`、`tertiary`、`inverseSurface`——这些没定义，会落回 M3 基线的紫色系。

实测对比度（WCAG 2.1）：

| 组合 | 比值 | 结论 |
|---|---|---|
| `#59625D` on `#FFFFFF`（次要文字） | 6.31:1 | ✅ AA |
| `#0F6B4F` on `#FFFFFF`（主色文字） | 6.49:1 | ✅ AA |
| `#C4622D` on `#FFFFFF`（**error：删除、失败**） | **4.09:1** | ❌ 低于 4.5:1 |
| `#B8C4BB` on `#FFFFFF`（outline：勾选框、边框） | **1.80:1** | ❌ 低于非文本 3:1 |
| `#7FD6B6` on `#121815`（深色主色） | 10.45:1 | ✅ |

做法：

1. **补齐角色**（P0）：`secondary*`、`tertiary*`、`surfaceContainer*`、`inverse*`、`scrim` 全部显式声明。推荐用 seed `#0F6B4F` 生成整套 tonal palette（Material Theme Builder），error 手工校正。
2. **error 偏浅**（P0）：浅色 error 改 `#A24617`（6.13:1），补 `errorContainer #FBE7DC` / `onErrorContainer #5A1E00`（10.84:1）；深色 `#F0A07A` 保留。
3. **outline 太浅**（P1）：组件边框改用 `#7D8C82`（3.53:1，满足非文本 3:1）；分隔线继续用 `#B8C4BB`，拆成 `outline` 与 `outlineVariant` 两个角色。
4. **禁止 UI 层写死颜色**（P0）：加 lint/detekt 规则，`Color(0x` 只允许出现在 `theme/`；现有 23 处逐条清理。

### 8.2 字阶：只覆盖了 5 档

现状：`AppTypography` 只定义 headlineSmall 24 / titleLarge 22 / titleMedium 16 / bodyMedium 14 / labelMedium 12，其余走 M3 默认，行高未设；文件大小、进度、时间戳等数字不等宽，刷新时会左右跳。

建议阶梯（工具类产品够用）：

| Token | 字号 / 行高 | 字重 | 用途 |
|---|---|---|---|
| headlineSmall | 24 / 32 | 600 | 首启标题、页面大标题 |
| titleLarge | 22 / 30 | 600 | 弹层标题 |
| titleMedium | 16 / 24 | 600 | 列表主文本、区块标题 |
| bodyMedium | 14 / 21 | 400 | 正文、说明 |
| labelLarge | 13 / 18 | 500 | 按钮 |
| labelMedium | 12 / 16 | 500 | 辅助信息 |
| labelSmall | 11 / 15 | 400 | 时间、路径 |

做法：

- 中文行高 1.5（英文 1.4），标题 1.3；
- 数字统一 `FontFeatureSettings = "tnum"`（进度、大小、剩余时间）；
- 字号全部用 `sp`，跟随系统缩放（见 8.8）；
- 中英混排不加空格，但"12 项""8 秒"这类数字 + 量词保留一个空格。

### 8.3 栅格、圆角、间距：需要一套刻度

现状：26 处 `RoundedCornerShape`，实际取值 12×10、18×5、99×3、14×3、999×2、22×1、28×1；间距出现 4/6/8/10/12/14/18/20/22/24/28。

建议：

- **间距只用 4 的倍数**：4 / 8 / 12 / 16 / 24 / 32；页面版心保留 20 或统一到 16/24。
- **圆角刻度**：4（输入框内元素）/ 8（小标签）/ 12（列表图标底）/ 16（卡片）/ 24（弹层顶角）/ 999（胶囊）。
- **行高**：列表 64dp（单行）/ 72dp（双行）；当前 60–64 混用，统一 64。
- **卡片**：白卡 + 1dp `outlineVariant` 描边，或 0 阴影；不要描边和阴影同时上。

### 8.4 图标与插画

现状：Material Outlined 与自绘混用；图标尺寸 17/18/21/22/23/24/36/42/48 八种；文件类型只有"文件夹 / 文件 / 压缩包"三种，`.zip` 和 `.rar` 长得一样。

做法（行业通行）：

- **24dp 网格、1.5dp 线宽、圆角端点**；内联 20dp；触控热区 ≥48dp。
- 做一套**文件类型图标**（压缩包按格式分色、图片、视频、音频、文档、代码、APK），16 种足够；颜色只取 3 个语义色，不要彩虹。
- 空态插画 2–3 张（空文件夹、空回收站、无任务），单色线性 + 主色点缀，不用 3D 或渐变。
- 品牌符号（Z）只出现在启动图、关于页和商店图，不要塞进列表。

### 8.5 动效：几乎没有，且有一处用错

现状：全项目只有 `ArchiveScreen` 的 `DreamPreviewBorder` 一处动画——预览页边缘无限呼吸光。它和"工具、可信、省电"的气质相反，还持续重绘。

建议动效规范：

| 场景 | 时长 | 曲线 |
|---|---|---|
| 按压反馈 | 90–150ms | 系统 ripple |
| 列表增删 | 200ms | FastOutSlowIn |
| Tab 切换 | 250–300ms | EmphasizedDecelerate |
| 弹层升起 | 300ms | ModalBottomSheet 默认 |
| 进度条更新 | 250ms 线性插值 | 不要跳变 |
| Snackbar 进出 | 150ms | 系统默认 |

做法：

- 删掉预览页呼吸光，改**静态 1dp 主色描边 + 顶部一行说明**（"仅预览，解压后才能使用"）；需要提示时用一次 300ms 淡入。
- Tab 切换用 `AnimatedContent` + shared axis（水平）。
- 列表用 `animateItemPlacement`，删除时 150ms 淡出。
- 尊重系统"减少动态效果"（`ANIMATOR_DURATION_SCALE == 0` 时全部直接切换）。

### 8.6 空态 / 加载 / 错误：三个模板

现状：空态只有一句"此文件夹为空"；加载是全屏圆形转圈；错误直接显示异常 message（如 `ENOSPC`）。

做法：

- **空态**：图标 48dp + 一句解释 + 一个主操作。例："这里还没有文件。去下载目录看看 →"
- **加载**：列表场景用骨架屏（6 行灰条），首屏超过 300ms 才显示，避免闪烁。
- **错误**：人话 + 原因 + 两个出口（重试 / 换个位置）；技术信息折叠进"详情"。
- 三态统一放在内容区居中，垂直位置约可视区 40%，不随内容高度漂移。

### 8.7 交互模型：五层叠加

现状：底部导航 + 选择工具条 + 解压 FAB + Snackbar + 边缘滑动手势同时存在；选择模式下 FAB 仍悬浮在右下，和工具栏的"解压"重复；Snackbar 居中，会压住列表行。

做法：

- **一屏一个主动作**：浏览时只有底部导航；进入选择模式后隐藏导航栏与 FAB，只留工具条（当前已隐藏导航，FAB 还没隐藏）。
- **Snackbar 位置**：底部导航上方 8dp、左对齐、最长 2 行，不要居中悬浮。
- **手势收敛**：只保留系统返回手势；自绘的左右边缘返回区（`EdgeSwipeBackZones`）容易和系统手势打架，建议删除，或缩到 12dp 且仅在没有系统手势时启用。
- **弹层高度**：最大 88% 屏高，键盘弹出时整体上移，主按钮始终可见。

### 8.8 无障碍

现状：`contentDescription` 55 处，其中 27 处为 `null`（多数是装饰图标，可接受）；部分图标按钮 34dp；error 文字对比度不足；200% 字号未验证。

做法（WCAG 2.1 AA + Material 指南）：

## 9. 多语言与本地化（i18n）专项分析

> 本章回答三个问题：i18n 到底是什么、Zippest 现在差多少、要做的话怎么分阶段做才不烂尾。

### 9.1 先把概念说清楚

- **i18n（internationalization，国际化）**：工程层面让产品**不绑定单一语言和地区**——所有文案外置成资源、日期/数字/大小按地区格式化、布局能伸缩、支持从右到左（RTL）。它是一次性架构投入。
- **l10n（localization，本地化）**：针对某个具体地区提供翻译和格式，例如 `zh-CN`、`en-US`、`ja-JP`。翻译只是 l10n 的一部分。
- **翻译 ≠ i18n**：不做 i18n 直接硬翻译，会得到“中文语序 + 英文单词”的界面，以及到处截断的按钮。
- **和文件名编码无关**：Zippest 里的 GBK / Shift-JIS 是**压缩包内文件名的编码**，解决“解压出来是乱码”；界面语言是另一回事，两者互不影响。

### 9.2 现状盘点（有证据）

- `res/values/strings.xml` 只有 `app_name` 一项；
- 约 **695 处**中文字面量散落在 Kotlin：`Text("...")`、Snackbar、对话框、错误提示、通知、`contentDescription`、设置项标题与说明；
- 已做对的部分：文件大小 `Formatter.formatShortFileSize`、相对时间 `DateUtils.getRelativeTimeSpanString` 会自动跟随系统语言；
- 还没做对的部分：排序用 `compareBy`（未用 `Collator`，中文拼音/英文大小写排序不理想）、所有文案硬编码、没有 per-app 语言入口；
- README、商店文案、隐私说明目前只有中文。

### 9.3 做不做：收益、成本、风险

**收益**

- Google Play 海外自然量（压缩工具是全球需求，且竞品普遍多语言）；
- 英文 issue / PR 的协作门槛下降，开源项目更容易被推荐；
- 专业感：设置里能切语言，是“成熟工具”的信号。

**成本**

- 一次性：抽取 3–4 人日 + 翻译 1 人日 + 校对 1 人日 + 回归 1–1.5 人日 + RTL 0.5–1 人日 ≈ **6–9 人日**（只做英文可压到 6 人日左右）；
- 长期：每加一个功能，文案要同步 N 种语言，维护成本约 +10–15%；翻译质量需要持续看 issue。

**风险**

- 翻译质量差比不翻译更伤口碑（“机翻感”）；
- 文本膨胀导致布局截断（德语普遍比中文长 30%+）；
- RTL 布局与手势方向容易漏；
- 术语不一致（“解压 / 提取 / extract / unzip”混用）。

**结论**：不建议一上来做“全量多语言”；按 9.9 分档，先做**英文最小闭环**。

### 9.4 技术方案（Android 侧）

**资源组织**

- 默认中文放 `values/strings.xml`，英文放 `values-en/strings.xml`；
- 复数用 `<plurals>`（英文 `1 file / 2 files`，中文只有 other）；
- 固定选项列表用 `<string-array>`（排序方式、冲突策略、编码选项）；
- 所有带变量的句子用整句 + 占位符 `%1$s`、`%1$d`，**禁止拼接**（语序不同会翻车）；
- 分组命名：`common_* / browser_* / archive_* / settings_* / task_* / error_*`。

**Compose 取词**

- `stringResource(R.string.xxx)`、`pluralStringResource(...)`；
- `contentDescription`、`Snackbar`、`AlertDialog`、通知渠道名、通知正文全部走资源；
- 不要在 `remember` 的 key 里放拼接后的文案。

**应用内语言切换**

- Android 13+：`LocaleManager.setApplicationLocales()` + `res/xml/locales_config.xml` + Manifest `android:localeConfig`；
- Android 12 及以下：`AppCompatDelegate.setApplicationLocales()`（AppCompat 1.6+）；
- 设置 → 外观 里加一行「语言」：跟随系统 / 中文 / English；
- 切换后 Activity 会重建，需确认返回栈与未保存状态（重命名输入框等）。

**格式与排序**

- 日期：新代码用 `java.time` + `DateTimeFormatter.ofLocalizedDate`；旧代码 `DateUtils` 可保留；
- 文件大小：继续用 `Formatter`，不要自己拼 "MB"；
- 排序：`Collator.getInstance(Locale.getDefault())` 做名称排序；类型排序用扩展名（本身与语言无关）；
- 数字：避免手写千分位。

**RTL**

- 布局用 `start/end` 而非 `left/right`（现有代码大部分已正确）；
- 返回箭头、播放箭头等方向性图标要镜像（`AutoMirrored` 图标）；
- `EdgeSwipeBackZones` 的左右手势在 RTL 下要互换；
- 用阿拉伯语（`ar`）跑一遍截图。

**字体**

- CJK、阿拉伯、希伯来都由系统字体覆盖，无需自带字体；
- 不要引入只含拉丁字符的自定义字体，否则日文/阿拉伯会变方框。

**不翻译的内容**

- `LICENSE` / `NOTICE` 全文、压缩格式名（ZIP / 7Z / RAR / TAR）、文件内容、README 的许可证段落。

### 9.5 代码改造步骤（按可回滚的 PR 拆）

1. **基建**（0.5 人日）：建 `values-en`、开 lint `HardcodedText`（先 warning）、加伪语言 `en-XA` 用于截图找截断；
2. **抽取**（3–4 人日，按屏幕分批）：错误与通知 → 设置 → 文件浏览 → 压缩包预览/解压面板 → 任务中心/回收站/关于；
3. **术语表**：压缩包 / 解压 / 压缩 / 分卷 / 密码 / 编码 / 条目 / 目标位置 / 同名文件 / 回收站，固定译法；
4. **翻译 + 校对**（2 人日）：AI 初翻 + 人工校对，重点看按钮（短）和错误提示（长）；
5. **回归**（1–1.5 人日）：按 9.8 清单逐项过；
6. **RTL**（0.5–1 人日）：单独 PR，只改方向性布局与手势。

### 9.6 翻译与协作流程

- 工具：Crowdin / Weblate（可自建）/ Transifex；小团队可直接用 Android Studio 翻译编辑器 + AI 初翻；
- 给每个字符串加**上下文注释**（在哪个界面、变量含义），否则「打开」会被译成 open / unlock / browse；
- CI 检查：`lint` 的 `MissingTranslation`、`ExtraTranslation` 设为 error，缺键直接挂；
- 版本策略：翻译随功能 PR 一起改，不攒批；
- 商店文案：Play listing 用 fastlane metadata 分语言；国内商店保持中文。

### 9.7 UI 适配风险清单

| 风险 | 表现 | 对策 |
|---|---|---|
| 文本膨胀 | 德语/俄语按钮文字溢出 | 按钮 `wrapContentWidth`、文案优先动词短语、避免 `maxLines=1` 硬截断 |
